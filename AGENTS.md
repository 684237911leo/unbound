# AGENTS.md — правила разработки UNBOUND

## Роли моделей

Принцип: **OPUS → HAIKU / SONNET → OPUS**.

| Модель | Роль | Когда |
|---|---|---|
| Opus | Координатор, архитектор, приёмка | Разбор команд пользователя, архитектура, разбиение задач, проверка результатов, сложные решения, документация-память |
| Haiku | Основной исполнитель (по умолчанию) | Экраны, меню, UI, компоненты, предметы, NPC по шаблону, диалоги, простые квесты, данные, конфиги, подключение ресурсов, тесты по готовым требованиям, мелкие фиксы |
| Sonnet | Исполнитель сложных задач | Сохранения и миграции, сборка/подпись Android, связка нескольких систем, сложная логика и алгоритмы, оптимизация, нестабильные компоненты, то, что Haiku не осилила |

Opus не пишет рутинный код сам. Модель исполнителя задаётся явно параметром `model` у субагента (`haiku` / `sonnet`). Если назначить нужную модель нельзя — сообщить пользователю, не имитировать делегирование.

## Эскалация Haiku → Sonnet

1. Haiku дважды не устранила одну и ту же проблему.
2. После её правок появились новые ошибки.
3. Нужна смена архитектуры.
4. Исполнитель не понимает зависимостей между компонентами.
5. Результат не соответствует требованиям.
6. Проблема затрагивает несколько связанных систем.

Если не справился и Sonnet — Opus разбирает сам. Повтор той же попытки без смены подхода запрещён.

## Постановка задачи исполнителю

Каждое задание содержит: цель; точные файлы, которые можно трогать (и которые нельзя); нужный контекст (выдержки из PROJECT_MAP.md / GAME_DESIGN.md, а не «изучи весь проект»); критерии готовности; обязательные команды проверки. Исполнители **не делают git commit** — коммитит Opus после приёмки.

## Отчёт исполнителя

- Что реализовано.
- Созданные файлы.
- Изменённые файлы.
- Принятые решения.
- Проведённые проверки (команды и результат).
- Найденные ошибки.
- Что осталось.

## Приёмка (Opus)

Opus проверяет фактические изменения (`git diff`, запуск `npm run typecheck`, `npm test`, `npm run build`, при необходимости скриншот через Playwright), а не только отчёт. Затем принимает или возвращает на доработку.

## Параллельная работа

- Независимые задачи с непересекающимися файлами — параллельно.
- Зависимые задачи или общие файлы (особенно `package.json`, `src/main.ts`, `src/core/*`, `android/`) — строго последовательно.
- Два агента никогда не редактируют один файл одновременно.

## Принципы качества

- Не создавать фиктивных механик (кнопка, которая «делает вид»).
- Не заявлять о готовности непроверенного.
- Не переписывать готовые модули без причины, не менять стек.
- Данные (персонажи, диалоги, квесты, предметы, корабли) — в `src/data/`, отдельно от логики.
- Не терять сохранения: формат версионируется, изменения — только через миграции (см. ARCHITECTURE.md).
- Не пересоздавать keystore, не менять alias и applicationId (см. SIGNING.md).
- После завершения целостной задачи обновлять PROJECT_MAP.md, PROGRESS.md, CHANGELOG.md.
- Не добавлять сюжетные факты (имя героини, предыстория, объект мести) без согласования с пользователем.

## Порядок работы над новой командой

1. Прочитать PROJECT_MAP.md и нужный раздел PROGRESS.md.
2. Определить затронутые компоненты, проверить только нужные файлы.
3. Составить план, раздать задачи.
4. Принять результат, обновить документацию, закоммитить.
